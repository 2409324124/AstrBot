# AstrBot Local RAG Stack

This stack keeps AstrBot's document parsing, chunk metadata, SQLite FTS sparse
retrieval, knowledge-base UI, and rank fusion. Dense embeddings are generated by
`BAAI/bge-m3` through an OpenAI-compatible Text Embeddings Inference endpoint and
stored in persistent Qdrant collections.

```text
AstrBot
  ├── SQLite doc.db: text, metadata, FTS5
  ├── POST embedding-server:8000/v1/embeddings
  └── Qdrant collection per knowledge base: 1024-d cosine vectors
```

The online chat LLM provider is unchanged during sidecar deployment. After the
independent Gateway passes acceptance, AstrBot can be reduced to QQ transport;
see `../agent-gateway/README.md`. Keep `AGENT_GATEWAY_ENABLED=false` until that
cutover.

The independent collection migration is additive and idempotent:

```bash
sudo docker exec astrbot python \
  /AstrBot/rag-stack/scripts/migrate_agent_rag_v1.py \
  --target agent_rag_v1 --batch-size 128

sudo docker exec astrbot python \
  /AstrBot/rag-stack/scripts/verify_agent_rag.py \
  --collection agent_rag_v1 --top-k 16
```

The migration reads `kb.db` in SQLite read-only mode to resolve document names,
upserts deterministic point IDs, and never deletes the old AstrBot collections.
The verifier runs all 31 tracked retrieval cases through the same BGE-M3 +
Qdrant dense/BM25/RRF request shape as the Gateway and prints no retrieved text.

## External research and group behavior

The RAG stack supplements, rather than replaces, current web research. The
AstrBot image accepts the Exa key only from the ignored `rag-stack/.env` file;
do not put it in `cmd_config.json` or commit it:

```bash
printf '\nASTRBOT_WEBSEARCH_EXA_KEY=replace-with-your-exa-key\n' >> .env
chmod 600 .env
```

After AstrBot is running, enable the Exa tool set through the reversible helper:

```bash
./scripts/configure_exa_web_search.sh apply
```

It refuses to enable search when the environment key is empty, updates only
`web_search`, `websearch_provider`, `web_search_link`, and
`verified_factual_reply_policy`, and stores their previous values under ignored
`runtime/`. Restore them with
`./scripts/configure_exa_web_search.sh restore`. Exa offers normal web search
and its `tweet` category through the same tool. The reply policy prefetches
web and X leads for factual requests, accepts only an allowlisted official,
academic, or established-news HTTPS source as evidence, emits a
program-controlled `可信来源：` footer when one is found, and appends
`（ai生成内容）` to verified/general replies or `（未经核验的消息）` when a
factual reply lacks trusted evidence. X is treated as a lead, never as
standalone proof.

`configure_group_behavior.sh apply` preserves the existing `concise_group`
persona and appends an audited group behavior extension. It keeps casual chat
short, but requires technical follow-ups to explain reasoning rather than only
name an algorithm; current, disputed, niche, or explicitly researched questions
must search first. The script saves the original prompt in ignored
`runtime/group-behavior-backup.json`; restore it with:

```bash
./scripts/configure_group_behavior.sh restore
```

Members can explicitly request a source-backed answer with
`/research 问题` (aliases: `/研究`, `/检索`). In the shared-QQ-account setup,
the human account takes a 15-minute, per-group priority lease whenever it sends
a normal message. Send `云洁：让我bot来回答这个问题` as a reply to hand the
quoted question back to the bot. A normal member saying e.g. `这群别开bot`
mutes the bot for 30 minutes in that group; group admins and the shared human
account bypass this temporary social mute.

Scheduled-task tools are intentionally disabled for this deployment. Apply the
reversible AstrBot configuration guard after the container is healthy:

```bash
./scripts/configure_agent_safety.sh apply
```

It changes only `provider_settings.proactive_capability.add_cron_tools`, saves
the previous value in ignored `runtime/agent-safety-backup.json`, and can be
reverted with `./scripts/configure_agent_safety.sh restore`. The independent
Gateway exposes no cron or reminder tool.

## Initial configuration

```bash
cd /home/miku/astrbot-deploy/AstrBot/rag-stack
cp .env.example .env
chmod 600 .env
```

Set strong random values for `QDRANT_API_KEY` and `EMBEDDING_API_KEY`, then set
the AstrBot dashboard username and password. Keep `ASTRBOT_VECTOR_DB=faiss`
during deployment and migration. `.env` is ignored by Git.

The TEI image and BGE-M3 model exceed 1 GB. On the remote server this download
must be started manually. If the local proxy is available on port 18081:

```bash
export HTTPS_PROXY=http://127.0.0.1:18081
export HTTP_PROXY=http://127.0.0.1:18081
./scripts/download-model.sh
sudo docker logs -f astrbot-embedding
```

The script uses a temporary host-network TEI container so the remote host's
loopback-only proxy is reachable. After the download it creates a stable
`/data/bge-m3` link, stops the temporary container, and starts the normal
bridge-network service from that local path. The Hugging Face cache is
persistent, so container recreation does not download the model again.

## Start and stop

Start only Qdrant and the embedding service:

```bash
./scripts/start.sh
```

Attach the existing AstrBot container to the RAG network while keeping FAISS:

```bash
./scripts/start.sh --with-astrbot
```

The override builds `astrbot-local-rag:4.26.5` from the currently cached AstrBot
image and adds the pinned Qdrant Python client. The source bind mount and all
existing data mounts remain unchanged. The build proxy defaults to the remote
host proxy on `127.0.0.1:18081`; clear `RAG_BUILD_PROXY` if direct PyPI access is
preferred.

Stop the RAG services only after rolling AstrBot back to FAISS:

```bash
./scripts/rollback.sh
./scripts/stop.sh
```

`stop.sh` refuses to stop Qdrant while `.env` selects it. `--force` exists for
emergency maintenance.

## Migrate existing knowledge bases

Create a safety backup before any provider change:

```bash
./scripts/backup.sh --skip-qdrant
```

Load `.env` and re-embed every existing SQLite chunk without modifying the
source databases or FAISS indexes:

```bash
set -a
source .env
set +a

sudo docker compose --env-file .env \
  -f ../../compose.yml -f astrbot.override.yml \
  exec -T astrbot python /AstrBot/rag-stack/scripts/migrate_kb.py \
  --result-file /AstrBot/rag-stack/runtime/migration-results.jsonl

sudo docker compose --env-file .env \
  -f ../../compose.yml -f astrbot.override.yml \
  exec -T astrbot python /AstrBot/rag-stack/scripts/verify_migration.py
```

Migration is idempotent. It preserves chunk IDs, document IDs, metadata, and
chunk boundaries. Rerunning it overwrites the same Qdrant points.

The current deployment should produce these exact counts:

- AI Infra: 192 chunks
- Deep-learning classic papers: 10,821 chunks
- Modern model atlas: 76 chunks
- Total: 11,089 chunks

Do not cut over if `verify_migration.py` reports missing or extra IDs.

## AstrBot configuration and cutover

`configure_astrbot.py` uses the authenticated dashboard API. It creates or
updates this provider:

```text
id: local_bge_m3
type: openai_embedding
base: http://embedding-server:8000/v1
model: BAAI/bge-m3
dimension: 1024
```

After migration verification, run:

```bash
./scripts/cutover.sh
```

The script:

1. Tests Qdrant and TEI.
2. Creates/tests the local embedding provider.
3. Saves every knowledge base's previous provider ID under `runtime/`.
4. Updates the knowledge bases through the AstrBot API.
5. Atomically changes `.env` to Qdrant.
6. Recreates only AstrBot; NapCat and QQ login are not recreated.

Rollback restores FAISS and the previous provider IDs:

```bash
./scripts/rollback.sh
```

Existing `index.faiss` files are never deleted.

## Historical CPU corpus

`corpus/history-cpu/` is a separately audited corpus for older Intel and AMD
platforms. It currently covers 503 distinct SKUs: Xeon E5/E7 v1-v4, Xeon
Scalable generations 1-3, desktop Ryzen 3/5 from Zen through Zen 2,
Threadripper 1000/2000/3000 and PRO 3000WX, and EPYC 7001/7002. The tracked
manifest records vendor-primary sources and import parameters; ignored ARK HTML
under `sources/` is only reproducible build input. Thirteen representative case
studies add NUMA topology, test systems, STREAM/HPL/HPCG, CFD or other HPC
applications, and explicit limits where direct finite-element data is absent.

Validate the documents, exact family counts, source links, and retrieval cases:

```bash
uv run python rag-stack/scripts/validate_history_cpu_corpus.py
```

The importer is additive: it creates a dedicated knowledge base, uploads only
missing declared documents, keeps resumable state under ignored `runtime/`, and
refuses unknown or modified remote documents. Missing documents are uploaded in
ordered batches of at most 10 files to respect the AstrBot API limit. It contains
no delete path. First
create a full backup and run the read-only plan:

```bash
set -a
source rag-stack/.env
set +a

uv run python rag-stack/scripts/import_history_cpu.py --dry-run
uv run python rag-stack/scripts/import_history_cpu.py \
  --apply \
  --backup-dir /mnt/PM983/astrbot-rag/snapshots/astrbot-rag-TIMESTAMP
```

An apply run requires a completed backup manifest with Qdrant snapshots. After
upload it verifies all 20 document names, nonzero chunk count, and 31 real
retrieval queries. Every query declares an `overview`, `example`, or `detail`
layer and one or more expected documents; a correct-looking number from the
wrong document fails verification. Historical CPU retrieval keeps overview
queries at 5 chunks, expands concrete examples to 8, and expands explicit
detail/full-report queries to 15; this conditional policy does not change other
knowledge bases or override a larger user-configured limit. The manifest also
proves exact coverage of
20 target generations, so a missing generation cannot be hidden by the document
count. It does not bind the new knowledge base to
any group or private chat; that remains an explicit dashboard/session
configuration step.

## Backup and restore

Create a full backup while services remain online:

```bash
./scripts/backup.sh
```

The backup uses SQLite's online backup API, copies FAISS indexes and AstrBot
configuration, creates one Qdrant collection snapshot per knowledge base,
downloads the snapshots, and writes a SHA256 manifest under
`${RAG_DATA_ROOT}/snapshots`.

Restore SQLite and FAISS only after reviewing the backup manifest:

```bash
./scripts/restore.sh /mnt/PM983/astrbot-rag/snapshots/astrbot-rag-TIMESTAMP --confirm
```

Restore first rolls AstrBot back to FAISS and stops only the AstrBot container
while copying databases. Qdrant snapshot files are preserved for explicit upload;
the restore script does not overwrite live collections automatically.

## Troubleshooting

### Embedding service is not ready

```bash
sudo docker logs --tail 200 astrbot-embedding
nvidia-smi
du -sh /mnt/PM983/astrbot-rag/hf-cache
```

Confirm the proxy is reachable before repeating the manual download. Do not
delete a partial Hugging Face cache; downloads can resume.

### Qdrant authentication or storage failure

```bash
sudo docker logs --tail 200 astrbot-qdrant
curl -H "api-key: $QDRANT_API_KEY" http://127.0.0.1:6333/collections
df -h /mnt/PM983
```

### A knowledge base fails to initialize

Check that its Qdrant collection dimension is 1024 and that `.env` contains the
same collection prefix used by migration. A dimension mismatch intentionally
blocks initialization to prevent corrupt retrieval.

### Immediate recovery

```bash
./scripts/rollback.sh
```

This is the supported recovery path. Never delete Qdrant storage or legacy FAISS
files while diagnosing a retrieval issue.

## Performance baseline

Start migration with batch size 32. Record total embedding time, GPU memory,
GPU utilization, Qdrant query latency, CPU use, and disk use before changing the
batch size. Then compare batch sizes 16, 32, and 64. At the current 11K-point
scale, keep Qdrant vectors and HNSW in memory; quantization and on-disk vectors
are unnecessary.

A reranker and Agent long-term memory are intentionally outside the first
cutover. Long-term memory should use a separate Qdrant collection rather than
mixing conversation memories with document chunks.
